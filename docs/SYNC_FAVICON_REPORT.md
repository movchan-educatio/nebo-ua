## Синхронізація: причини й межі доказів

Відтворено такі дефекти коду:

1. UkraineAlarm записував `lastActionIndex` окремо й раніше за публікацію
   відповідного snapshot. Якщо публікація не відбулася, наступний version gate
   міг підтвердити старий набір як актуальний. Окрема проблема: перенесення
   grace-записів замість точного підтвердженого набору могло відновлювати вже
   відсутню тривогу після відповіді з порожнім набором.
2. Спільний бар'єр очікування джерел затримував публікацію моніторингу до
   завершення всіх послідовних UkraineAlarm status/alerts/regions-запитів.
3. Успіх одного джерела дозволяв збільшувати лічильник пропусків записів
   іншого, недоступного джерела. Помилка не є підтвердженим відбоєм.
4. Трихвилинний KV gate обмежував також публікацію нових моніторингових
   подій. Перевірка KV перед записом не була атомарним захистом від старішого
   запуску cron.
5. Свіжі рядки D1 `checks` накладалися на старий KV snapshot. Час успішного
   fetch міг виглядати часом перевірки вмісту, який не було опубліковано.
6. Резервний frontend міг позначати NEPTUN як доступність OFFICIAL;
   відсутній timestamp замінювався поточним часом. Джерело зі старим
   успішним snapshot залишалося «онлайн» без перевірки віку.

Це доведені механізми можливих затримок і хибної свіжості. **Причину саме
інциденту «07:54 / 07:45» та upstream 401 не встановлено**: не було доступу
до production Cron/CPU/D1 logs. Публічні `/v1/state` і `/v1/metrics` з цього
середовища відповідали 403. Це не доказ 403 від UkraineAlarm і не доказ
неправильного API-ключа.

### Внесені зміни

- Поточний стан зберігається в **існуючій D1**: snapshot, попередні записи,
  точний набір OFFICIAL і його version gate записуються одним UPSERT.
  Умова версії відкидає завершення старішого циклу після нового. При однаковому
  мілісекундному старті конкуруючий запис також консервативно відхиляється.
- Джерела стартують паралельно. UkraineAlarm має загальний deadline 9 с на
  всю операцію; NEPTUN — 19 с, MAPA — 25 с поверх їхніх наявних обмежених
  повторів. Після готовності моніторингу незавершений UkraineAlarm може
  відкласти першу публікацію максимум на 50 мс очікування його відповіді;
  час власне обробки й D1 залишається окремим. Пізніше публікується його результат.
- 401/500/timeout OFFICIAL не видаляють офіційних тривог: останній стан
  зберігається зі `stale`, помилкою та незмінним часом успіху. NEPTUN/MAPA
  продовжують публікувати доступні дані. OFFICIAL не замінюється їхнім статусом.
- Пропуски рахуються лише після успішної перевірки відповідного джерела.
  Дві публікації одного циклу не подвоюють пропуски. Відмова NEPTUN alerts
  не приховує успішний NEPTUN threats.
- KV gate і heartbeat залишилися для резервної копії. Вони більше не
  затримують D1 `/v1/state`. Відмова KV не зупиняє D1. Відмова D1 зупиняє
  запис і дозволяє явно позначений `kv-fallback` з його власними старими часами;
  якщо копії немає, відповідь — 503. KV залишається eventually consistent,
  тому fallback не має гарантій актуальності основного D1 стану.
- Журнал та push обробляються після публікації, їхні помилки фіксуються
  окремо. Вартість D1 читань/записів і CPU треба виміряти у staging;
  безкоштовність за будь-якого навантаження не гарантується.
- Для великих snapshot додано gzip понад 500 KB та явну відмову понад
  1,9 MB після кодування. Це враховує ліміт D1 2 MB, не відкидаючи записи.
  Відтворюваний тест використовує 1500 MAPA-подій і справжню SQLite schema.
- UI пише «Перевірено», зберігає час останнього успіху при відмові, не
  відновлює старішу публікацію поверх нової. Після 3 хв без підтвердження
  показує затримку. Резервний режим позначений як degraded.

### Аудит UkraineAlarm 401 та кількості запитів

401/403 тепер описують фактичний HTTP-статус без висновку «ключ неправильний»
або «це WAF». Схему авторизації не змінено, секрети не читалися й не
перевидавалися. Для UkraineAlarm не додано автоматичних retry після 401.
Наявна пауза після 429 збережена. Масових звернень до провайдера не було.

Один звичайний цикл робить status-запит; зміна індексу додає alerts, а
відсутній/прострочений довідник — regions. Незмінний індекс не потребує
повного alerts. Виправлено продовження кешу незміненого довідника після
закінчення його freshness. Публічний history endpoint також може робити
окремий upstream-запит. Перекриття cron або авторизований ручний refresh
можуть додавати цикли; захист запису не є глобальним HTTP mutex.

`checks` — це результати перевірок джерел, **не лічильник HTTP**. У циклі є
до трьох таких записів. Пауза після 429 може створити невдалий check без
нового HTTP-запиту, а кілька HTTP-запитів одного адаптера — один check.
Запити history взагалі не є cron check. Тому числа «1125 невдалих / 106
успішних» без вихідного SQL, інтервалу й логів не можна оголосити кількістю
HTTP-запитів або підтвердити їхнє походження.

Додано безпечний JSON-log на кожну фактичну UkraineAlarm HTTP-спробу:
`upstream`, path без query, status, durationMs. Без ключів, заголовків
авторизації й тіл відповідей. `/v1/metrics` тепер обмежує записи реальним
24-годинним вікном, а не лише кількістю останніх рядків.

### Спостережуваність pipeline

| Етап | Доказ / вимірювання | Що ще невідомо |
|---|---|---|
| CRON | Розклад у Git — 1 хв; JSON-log циклу містить startedAt, outcome, durationMs. | Реальна кількість запусків, останній успіх/збій, CPU Cloudflare. |
| FETCH | Окремі deadlines, per-source latency/health; UA HTTP-attempt logs. | Production latency, кількість 401, причина відповіді постачальника. |
| NORMALIZE → CORRELATE → FUSE | Сумарний `stagesMs.normalizeCorrelateFuse`, збережені оптимізації; 1500-подійний тест. | Окремий production CPU кожної функції. |
| STORE → PUBLISH | `stagesMs.publish`, D1 CAS, тести старішого запуску та відмов сховищ. | Remote D1 затримки, квоти й реплікація в обліковому записі. |
| JOURNAL / PUSH | `journalAndPush`, прапорці помилок, публікація перед цими діями. | Реальна доставка push у цьому прогоні не перевірялася. |
| FRONTEND | Локальний браузер → Worker API → SQLite → UI; 20-секундне polling збережене. | Реальні мобільні пристрої та мережа користувача. |

## Google favicon

На публічному сайті до змін `/favicon.ico` повертав **404 text/html**,
а `/assets/brand/favicon.svg` — 200 image/svg+xml. У head був SVG icon і
192px apple icon. Прямих посилань на Vercel favicon у перевіреному коді не
знайдено. Це підтверджені недоліки конфігурації; точне рішення Google щодо
раніше збереженої іконки без Search Console/історії crawl невідоме.

Використано існуючий radar favicon `assets/brand/favicon.svg`, узгоджений
з `assets/brand/logo-mark.svg` у шапці; нового логотипа не створено.
Темна підкладка зберігає читабельність на світлих і темних поверхнях.

| Файл | Розмір / формат | Локальний HTTP |
|---|---|---|
| `/favicon.ico` | ICO з кадрами 16, 32, 48 | 200, image/x-icon |
| `/favicon-32x32.png` | PNG 32×32 | 200, image/png |
| `/favicon-48x48.png` | PNG 48×48 | 200, image/png |
| `/favicon-192x192.png` | PNG 192×192 | 200, image/png |
| `/favicon-512x512.png` | PNG 512×512 | 200, image/png |
| `/apple-touch-icon.png` | PNG 180×180 | 200, image/png |
| `/favicon.svg` | Існуюча векторна версія | 200, image/svg+xml |
| `assets/icons/icon-192.png`, `icon-512.png`, `icon-maskable-512.png` | PWA; останній 512×512 із запасом для маски | Розміри й декодування перевірені локально |

Head головної, інформаційних сторінок, widget і 404 тепер посилається на
ICO/PNG та apple 180. Manifest має PNG 192/512 і maskable. Версію shell
cache підвищено; API, включно з `/v1/`, обходять SW cache; відсутнє зображення
більше не підміняється HTML offline-сторінкою. Canonical, title/description,
theme-color та robots не потребували SEO-переписування. Robots дозволяє
обхід; Vercel rewrite-конфігурації, що підміняє іконку HTML, у repo немає.

У поточних вимогах Google вказані квадратні іконки, рекомендовано понад
48px; PNG та ICO є в переліку форматів. SVG у цьому переліку не зазначений.
Надані стабільні raster URL відповідають цим вимогам. Після дозволеної
публікації треба перевірити реальний HTTP/Content-Type і доступність для
Googlebot та запросити повторний обхід головної через Search Console.
Google може обробляти зміни кілька днів/тижнів і не гарантує показ.
**Іконку в результатах Google ще не підтверджено зміненою.**
